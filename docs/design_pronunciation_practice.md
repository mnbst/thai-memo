# 発音練習（声調）の設計

## 目的

「声調が難しい」という声への回答。例文詳細画面で、お手本を聞いたあとに自分で発声し、
音節ごとに声調が合っているかを視覚的に返す。

既存の資産（`ThaiToneAnalyzer` による音節ごとの声調判定、`SentenceAudioPlayer` の
リピート再生）がそのまま土台になる。サーバー変更・LLM原価ともに不要で、
判定は完全にオンデバイスで完結する。

## スコープ

| フェーズ | 対象 | 置き場所 |
|---|---|---|
| 0 | 判定ロジックの検証（デバッグ画面） | 本番UIには出さない |
| 1 | **例文単位**の発音練習 | `detail_screen.dart` の `SentenceAudioPlayer` 直下 |
| 2 | 単語単位の発音練習 | `ToneExplanationDialog` 内 |
| 3 | 声調別の弱点レポート | 設定 or 学習状況 |

本ドキュメントはフェーズ0〜1を対象とする。

## 前提となる制約

端末TTS（`flutter_tts`）からは**再生時間も現在位置も取得できない**
（`sentence_audio_player.dart` 冒頭のコメントに既記）。したがって
「お手本が流れながらバーが進み、そこに自分の声を重ねる」同時カラオケ型は実現できない。

採用する形は **聞く → 録音 → 重ねて比較**（逐次）。
横軸は時間ではなく**音節**とし、お手本カーブは静的に描く。

学習法としてはシャドーイングではなくリピーティングにあたり、
初学者にはむしろこちらが適している。

## UI

### 配置

`detail_screen.dart:155` の `SentenceAudioPlayer` の直下に練習セクションを追加する。
既存プレイヤーには手を入れない。

```
[▶] ━━━━━●━━━━━━         ← 既存の全文再生（変更なし）

── 発音してみる ──────────────
   ↗ ＼ → ↗           ← お手本カーブ（音節列）
   [🎤 押しながら発声]
```

### 状態遷移

```
idle → recording → analyzing → result
                                 ├→ retry（同じ文をもう一度）
                                 └→ idle
```

- 録音は**押しっぱなし**（長押し）で、離したら解析。無音タイムアウトでの自動停止は入れない
  （タイ語は語間に無音が入りにくく、誤判定で切れる）
- 解析はオンデバイスで完結し、数百ms以内に結果を返す

### 結果表示

文が20〜30音節になると全音節を並べると潰れるため、**語単位に集約**して返す。

```
ผม  ชอบ  อาหาร  ไทย  มาก
━━  ━━   ━━━   ━━   ━━
緑   黄    緑    緑    赤     ← 語ごとの帯

（語をタップ → その語の音節カーブを拡大表示。お手本と自分を重ねる）
```

- 3段階：**○（合っている）/ 惜しい / ×**
- 「惜しい」を必ず用意する。2値だと挫折する
- **語の帯は最も悪い音節ではなく、合っている割合で決める。** 1音節でも外すと語全体が
  赤くなる作りでは、大半が合っている語まで赤くなりどこを直すか分からない。
  合っている＝1・惜しい＝0.5 として平均し、`kWordCorrectRatio` 以上で合格。
  実機で 0.75 では緩く、2音節の語は片方を落としても○のままだった（(1+0.5)/2）ので
  **0.9**（ほぼ全部合っていること）まで上げた。1にはしない
- 総合スコアは出すが小さく。点数より「どこが違うか」を主役にする
- 語タップの拡大表示が、そのままフェーズ2（単語単位練習）の入口になる

## 判定アルゴリズム

### 1. お手本カーブの生成

`sentence.wordBreakdowns` を `wordOrder` 順に並べ、各 `word.syllables` を連結して
文全体の音節列を得る。`syllables` が欠けている語は `Syllable.fromText()` で
クライアント側補完できる（`parseSyllables` が既に同じことをしている）。

各音節の `tone`（mid/low/falling/high/rising）に対し、話者正規化された
標準F0カーブを定数テーブルとして持つ。正規化時間 0..1 を10点でサンプルした値
（縦軸は声域内の相対位置 -1..1）。

| 声調 | 概形 |
|---|---|
| 中平声 mid | 中央付近で平坦、末尾がわずかに下降 |
| 低平声 low | 低い位置で平坦〜わずかに下降 |
| 高平声 high | 高い位置、後半でわずかに上昇 |
| 下降声 falling | 高く始まり急降下。ピークはやや後ろ |
| 上昇声 rising | 低く始まり、一度沈んでから上昇 |

`tone` が `unknown` の音節は判定対象外とし、グレーで表示する。

### 2. F0抽出

- `record` で PCM 16bit / 16kHz / mono を取得
- 窓 40ms、ホップ 10ms でフレーム化
- YIN（`pitch_detector_dart`）でフレームごとに F0 と confidence
- 無声・低信頼フレームは欠測扱い
- **信頼度だけで有声を決めてはいけない。** YIN は暗騒音や空調のハムのような
  弱い周期性にも高い信頼度を返すので、**押しはじめの無音が「発声した区間」として
  取り込まれる**。前後の無音は解析側で切り落としているが、それは無声フレームに
  限るのですり抜ける。害は先頭が汚れることに留まらず、DTW がその区間も音節に
  割り当てざるを得ず、**お手本の先頭の音節が無音とつき合わされて以降の対応づけが
  丸ごとずれる**。

  フレームの音量（RMS）が伴わないピッチは声ではないので落とす（`gateByEnergy`）。
  閾値は絶対値では置けない（マイクの利得も声量も端末と場面で変わる）ので、
  その録音自身の代表音量に対する比で決める（`kMinFrameEnergyRatio` = 0.06、約 -24dB）。
  代表音量は**最大値ではなく90パーセンタイル**を採る。リップノイズやボタンを
  押した音ひとつで基準が跳ね上がり、発話そのものが無音扱いになるため
- **メディアンフィルタ（5フレーム）を必ず通す**。YIN はオクターブエラーを出すため、
  これを省くと下降声が上昇声に化ける
- **セミトーン変換**：`12 * log2(f0 / ref)`。Hz の線形値で扱わない。
  知覚も声調も対数スケールであり、線形のままだと低い声の話者で判定が壊れる

### 3. 自己正規化（明示キャリブレーションを置かない理由）

声調は絶対音高ではなく**声域内の相対位置**で決まるが、その基準は録音自体から取れる。
文には複数の声調が混ざるため、1回の発話の F0 分布からレンジが推定できる。

```
m     = median(semitones)
range = percentile(95) - percentile(5)     ← 外れ値に強い値を使う
z     = (semitone - m) / (range / 2)       ← -1..1
```

**お手本カーブにも同じ正規化を掛ける**（`normalizeSelf`）。お手本の「±1＝声域の端」
という取り決めと、録音側のパーセンタイル正規化は尺度が一致しない。実際の声調カーブは
声域の端まで振り切らないため、正しく発音しても録音側の値が2割ほど大きく出て、
系統的な誤差として採点に乗ってしまう。両側に同じ変換を掛けることで、この文を
正しく読んだときの広がりが基準になる。

事前に「あー」と言わせる工程は不要。

**声域プロファイルの蓄積**：発話が短い、あるいは平坦な声調ばかりでレンジが
十分に取れない場合に備え、過去の録音から得た `m` / `range` を移動平均で保持し、
今回の推定が不安定なときはそちらを使う。UIには出さない暗黙のキャリブレーション。
フェーズ2（単語1語）ではこの蓄積が前提になる。

### 4. 音節境界の対応づけ

ユーザー音声のどこが何番目の音節かを決める必要がある。
有声区間の数と音節数は一致しない（タイ語は音節間で有声が途切れにくい）ため、
区間検出のヒューリスティックは積まない。

**DTW（動的時間伸縮）でお手本カーブ列とユーザーの z 系列を対応づける。**
境界を明示的に推定せずに済み、話速のばらつきも吸収する。
実装量は増えるが、等分割やエネルギー谷による境界推定より明確に堅い。

**帯（Sakoe-Chiba band）を必ず掛けること（`kDtwBandRatio` = 0.06）。** 制限しないDTWは全体の距離を
最小化しようとして経路を大きく歪め、**誤った音節が隣からフレームを盗んで
自分の誤りを隠す**。実測での被害:

| 取り違え | 帯なし | 帯あり |
|---|---|---|
| 低平→高平 | level 0.002（検出不能） | level 1.821 |
| 低平→中平 | level 0.006（検出不能） | level 0.748 |
| 下降→上昇 | shape 0.343（傾きが -1.51 と反転して測れていた） | shape 1.582 |
| 中平→高平 | level 0.409（すり抜け） | level 0.542 |

上昇声で発音した音節に13フレームしか割り当てられず、しかも下降と測れていた。
誤りを見逃すだけでなく、正しい発話も不安定に採点されるため
「厳しい・当てにならない」という体感になる。閾値の問題ではない。

**帯は 0.10 でもまだ緩い。** 実測で、上昇声で発音した音節の傾きが -0.81（下降）と
測れていた（隣の下降部分を借りていた）。0.06 まで締めて実際の発音と一致する。

### 無声区間を捨ててはいけない

子音（破裂音・摩擦音）でピッチが取れない区間を落とすと時間軸が縮み、しかも
縮み方が音節ごとに違う。帯は「時間が比例している」ことを前提にしているので
この歪みを吸収できず、カーブも有声区間の継ぎ目で垂直に跳んで見える。

短い無声区間（120ms まで）は補間して時間軸を保つ。ただし**補間したフレームは
採点に使わない**（実際の声ではない）。対応づけにだけ使う。

さらに、お手本と録音は**対応づいた同じ区間どうし**で比べる。録音側が音節の一部
しか声を出していないとき、お手本の全体と比べると、子音で隠れた部分（下降声の
ピークなど）を「出せていない」ことにされてしまう。

### 5. 採点

DTW で対応づいた区間ごとに2つの指標を取る。

- **形**：カーブそのものの一致（相関）。位置のずれも振れ幅の違いも問わない
- **つながり**：隣の音節との段差が、お手本の段差からどれだけずれているか

| 判定 | 条件 |
|---|---|
| ○ | 形・つながりとも閾値内 |
| 惜しい | 片方だけ閾値内 |
| × | 両方とも外れ |

### 何を根拠にするかは声調で決まる

| 声調 | 根拠 | 理由 |
|---|---|---|
| 下降声・上昇声 | **形** | 動きそのものが情報。振れ幅は問わない |
| 中平・低平・高平 | **直前との対比** | どれも平らで、形では互いに区別できない |

両方を全声調に課すと「形は合っているのに違います」が出る。声調ごとに情報の
乗っている場所が違うので、根拠もそれに合わせる。

短母音・死音節は下降声・上昇声でも動きを出しきれないので、形を根拠にできない。
直前との対比に回す。

### 形は「グラフとして同じ形か」で見る

相関係数を使う。**位置のずれと振れ幅の違いは自動的に無視される**ので、
短い音節で振れ幅が足りなくても、お手本ほど大きく動けなくても、形が同じなら通る。

**振れ幅は問わない。** 実測では、形がほぼ一致（corr 0.73〜0.99）していても
振れ幅がお手本の4割ほどしか出ない発話が普通にある。そこを弾くと練習にならない。

この代償として**下降声を中平声で発音した場合を見逃す**。実測の「正しいが弱い下降」
（お手本の38%）と、合成した「中平声で代用」（46%）は数値的に重なっており、
**両者を分ける閾値は存在しない**。弾く側に倒すと正しい発音まで巻き込む。

### 測れていない音節は採点しない

実測フレームが5本（50ms）未満の音節は判定対象外にする。数フレームだけ拾えた音節は
平均も傾きも当てにならず、そこに極端な値が出ると**隣との段差まで壊れる**。
実機では、この保護が無いときに先頭2音節の段差が他の7倍（1.7 対 0.25）になった。

**形は向きだけを見る。傾きの大きさは比べない。** 大きさを比べると、正しい方向に
動いていても「振れ幅が足りない」で弾かれる。実際、高平声を正しく出しても平らに
寄るのが普通で、お手本どおりの上昇幅を要求するのは無理がある。

この粗さはタイ語の声調体系とも合う。中平・低平・高平は平ら、下降と上昇だけが
動く声調で、実測の傾きも 中平 -0.29 / 低平 -0.46 / 高平 +0.76 に対し
下降 -1.86 / 上昇 +1.30 とはっきり分かれる（境界 `kFlatSlopeThreshold` = 0.8）。
**平らな3つの区別は形ではなく「つながり」が受け持つ。**

**声域内の絶対的な高さは採点しない。** 高さは話者・場面・文中の位置で素直に動く。
実際の声で試すと、正しく発音していても高さの差で弾かれることが多く、練習として
続かなかった。

一方、隣との段差は声調の情報を保つ。中平声と低平声のように形が同じで高さだけが
違う対立も、段差の変化として捕まえられる。形だけを見ると原理的に区別できないが、
つながりを足すことで拾える。

つながりは**直前との段差だけ**を見る。声調は前から順に聞こえてくるもので、
「直前と比べて上がったか下がったか」がそのまま手がかりになる。後ろとの段差は
同じ情報を2度数えるだけで、しかも次の音節が誤ったときに巻き添えを増やす。
**末尾の音節も途中と同じ扱い**で、後ろを見ない。

**そのぶん直前が誤ると、自分の段差も崩れる。** 実機で、中平声が高さのずれ 0.07・
相関 0.99 と完璧なのに、隣が崩れているだけで落ちた。このとき段差はこの音節に
ついて何も語っていないので、自身の高さで判断する（`kExactLevelEscape` = 0.35、
形の一致も併せて要求）。絶対的な高さは普段は採点しないので、**ほぼ一致している
ときだけ**に限る。合成音声で最も差の小さい取り違えでも 中平→上昇 が 0.19 だが、
そちらは形が合わないので通らない。

**直前が誤っていたときは、この許容を広げる**（`kBrokenNeighborEscape` = 0.50）。
段差が崩れていても、原因がどちらの音節かは分からないので、自身のグラフを信じる
側へ倒す。誤りが1つなら判定に影響しない（誤った音節自身は、その直前が正しいので
通常の上限で見る）。実機で、高平声を上げそこねた次の低平声が段差 1.501 で誤りに
されたが、その音節自身は高さのずれ 0.01・相関 0.98 だった。

**段差そのものを捨ててはいけない。** 直前が誤っていたら段差を使わずグラフだけで
見る、という形も試したが、悪化した。実機で、話者の中平声が2つ続けてお手本より
0.5〜0.7 高い箇所があり、段差では正しく通っていたものが高さで弾かれた。
段差は話者の音域のずれを打ち消すので、**多少崩れていても捨てるより使うほうがよい**。

### 文頭はピッチのグラフだけで見る

文頭には比べる相手がいない。段差を使わず、**その音節のグラフそのもの**で判断する。

- 下降声・上昇声 → 形（他の位置と同じ）
- 中平・低平・高平 → 形では互いに区別できないので、**声域内の高さそのもの**
  （`kGraphLevelGate` = 0.40）

高さは普段は採点しないが、録音側もお手本側も同じ手順で正規化してあり、
declination の効かない文頭は文中で最も高さが安定している位置でもある。
合成音声では文頭の取り違えは 0.48〜0.87 に出る。

平らであるべき音節が**逆向きに動いていれば別の声調**なので、そこだけは形でも弾く。
ただし合格ラインよりずっと緩く、「はっきり食い違っている」ときだけ落とす
（相関が負、かつ向きが違う）。お手本がほぼ平坦で相関が細かい揺れを拾うため、
締めると正しい発話を巻き込む。これで 中平→上昇（高さのずれ 0.19、相関 -0.17）を
拾えるようになった。

### 形は、形が出るだけ測れたときだけ根拠にする

高さは数フレームでも代表値が出るが、**形はそれでは決まらない**。実機で、
5フレーム（50ms）しか取れなかった下降声の相関が -0.52 と出て弾かれた。
出ていない形を根拠に誤りと言ってはいけない。`kMinVoicedFramesForShape` = 10
（100ms）に満たなければ、つながりで判断する。

### 声調の引っ張られ（carryover）はお手本に入れない

下降声の直後の高平声が、実機の5回すべてでお手本より 0.75〜1.44 低く出た。
下降声は低く終わるので、次の音節の入りがそこへ引っ張られる（carryover）という
説明が立つ。**そこでお手本側に入れて確かめたが、合わなかった。**

10音節の実測に対し、引っ張りの強さと届く範囲を振って段差の誤差を合計した結果:

| 引っ張り | 合計誤差 |
|---|---|
| 無し（現状） | 3.92 |
| 強さ0.5・音節全体 | 3.99 |
| 強さ1.0・音節の6割 | 3.98 |

**当該の音節は直る（0.37 → 0.02）が、他の4音節が同じだけ悪化する。**
合計は変わらない。carryover の形をした誤差ではないということなので、入れない。

残るのは「短い高平声を、直前の下降声から上げきれていない」という発話側の癖
（tonal undershoot）という説明で、これは Close で正しい。

### お手本も、録音と同じ手順で正規化する

録音側は declination も発話末の下がりも**含んだ状態**で声域を推定し、そこで
正規化しています。お手本だけを足す前の分布で正規化すると、**2つの尺度がずれます。**

音節の長さが揃っているうちは、このずれは 0.01〜0.16 に収まっていて見えませんでした。
長さを変えた合成音声（正しい発話）で測ると **0.35〜0.68 に跳びます。**
実際の発話の音節長は3倍以上ばらつくので、常にこの状態でした。

しかも害は高さだけで終わりません。カーブが合わないぶん **DTW が経路を歪めて
帳尻を合わせる**ので、音節の境界まで動きます。同じ合成音声で、30フレームの音節に
15フレームしか割り当たっていませんでした。

**足したあとで、もう一度正規化します。** これで両側の手順が揃います。

| 正しい発話（長さがばらつく合成音声） | 高さのずれ | 境界（真値 30/18/30/30/18/30） |
|---|---|---|
| 正規化を揃える前 | 0.13〜0.58 | 22 / 33 / 15 / 37 / 19 / 31 |
| 揃えたあと | 0.02〜0.14 | 30 / 20 / 28 / 27 / 22 / 30 |

### 音節の長さをお手本に持たせる

お手本の点数は、**そのままお手本側の時間の割り当て**になります。全音節を10点ずつに
すると「どの音節も発話時間の等分」と主張することになり、DTW の帯（対角線から6%）が
実際の長さの偏りを吸収しきれません。

実機で、10フレームしか無い音節の境界が**帯の限界にぴったり張り付きました**
（お手本の位置 0.200 に対し録音側 0.141、差 0.059 対 許容 0.06）。DTW はもっと
動きたかったのに動けず、隣の音節が 40 フレームを飲み込んで、その2音節だけが
誤判定になっています。

**「短母音 または 死音節」でまとめてはいけない。** 長母音に閉鎖音が付いただけの
音節（มาก, พูด）は長い。実機で、この判定で「短い」とされた音節が発話の 16% を
占め（予算は 7%）、そのずれで隣の音節の境界が帯に張り付いた。

| 音節 | 点数 |
|---|---|
| 長母音（生・死どちらも） | 10 |
| 短母音＋生音節（กัน, นั้น） | 8 |
| 短母音＋死音節（รัก, จะ） | 6 |

タイ語の母音の長短は**音韻的な対立**（語が変わる）で、話者や文脈で消えないので
決め打ちの資格があります。長短比はおよそ 1:1.5〜2。

**声調の振れ幅を縮めるかどうか（`shortSyllables`）とは別の判断です。** あちらは
「動きを出しきる時間があるか」で、閉鎖音で切られる死音節は長母音でも当てはまる。
長さと、動きの完了は別物。同じフラグを2つの目的に使っていたのが誤りでした。

**声調による長さの違いと文末の伸びは入れていません。** どちらも報告はありますが
差が小さく、この判定器で観測できていません。観測していないものをお手本に足すと、
何が効いているのか分からなくなります。

### 実際の発話に合わせた2つの補正

お手本カーブは声調の理想形なので、実際の発話で必ず起きる変形を入れておかないと
正しい発音が不当に罰せられる。

- **declination**：文が進むにつれて全体のピッチが下がる。入れないと文末に近い
  音節ほど低いと判定される。文末の丁寧語尾（ครับ / ค่ะ）は毎回その位置に来るため、
  影響が常に同じ語へ集中する。**正規化を済ませてから足すこと**（先に足すと分母が
  膨らみ、声調どうしの高さの差が縮む）。録音側から推定して取り除く方法も試したが、
  6音節程度の文では推定した傾きが先頭・末尾の音節の声調そのものを吸収して悪化した
- **下降声の連続**：下降声は高く始まって急に落ちる。直前も下降声だと低い位置から
  始まるので高い開始位置まで戻りきれず、下降幅が実際には小さくなる。毎回フルの
  下降を描くと連続した2つ目が必ず「足りない」と判定される。縮めるのは2つ目だけ
- **短母音・死音節**：時間が足りず、上昇声・下降声でも動きが完了しない
  （tonal undershoot）。お手本の振れ幅を縮めるだけでなく、**この音節では形を
  要求せず、隣との高低差だけで判断する**。出せないものを求めても意味がない。
  判定には `Syllable.hasShortVowel` と `syllableType`（dead）を使う。

  ただし**短くても形が出ていたなら、合格の根拠にしてよい**。短さが免除するのは
  「形を要求すること」であって、出せた形を捨てる理由にはならない。実機で、文頭の
  短い下降声（พรุ่ง）が corr=0.99 と形は完璧なのに Close に落ちていた
- **発話末の下がり（final lowering）**：declination とは別に、発話末では追加で
  ピッチが落ちる。直線の傾きだけでは見込めず、**末尾の語だけが毎回弾かれる**。
  文末の丁寧語尾（ครับ / ค่ะ）は必ずこの位置に来るので影響が同じ語へ集中する。

  **音節の中で傾きとして当ててはいけない。** 下降声の下がりに上乗せされて
  お手本が急降下し、到達できない形になる（実機で末尾の下降声が毎回 Close に
  なった）。位置のずれ（音節全体を一定量下げる）として当てる。採点で見るのは
  形と前後の対比なので、位置として当てれば対比だけに効いて形は歪まない。

閾値は合成音声での実測から決める。`calibration_test.dart` が両側を守る。

|  | 値 |
|---|---|
| `kFlatSlopeThreshold` | 0.8（平らとみなす傾きの上限） |
| `kDtwBandRatio` | 0.06 |

### つながりの合格ラインは声調ごとに変える

| 声調 | 合格ライン |
|---|---|
| 下降声・上昇声 | 0.45 |
| 高平声 | 0.40 |
| 中平声・低平声 | 0.35 |

下降声・上昇声はふだん形で通るので、この値が効くのは短い音節や形が測れなかった
ときだけ。締めると短母音の undershoot を許せなくなる（上昇声を平坦に言った短い
音節で 0.434）。平らな3つは高さの関係しか手がかりが無いので、そちらを締める。

**音節の高さは中心で測る**（正規化時間の中央60%）。入り際・抜け際は隣の音節から
移る途中なので、その音節の高さを表さない。平均で測っていたときは、実測フレームが
10本程度の音節で入り際に引っ張られ、同じ発話で同じ音節の段差が 0.53 と 1.42 に
振れた。

**中心は「お手本側の位置」で決める。フレーム数で端を削ってはいけない。**
対応づいた録音フレームを端から数えて削ると、DTW の対応づけが少し動いただけで
「音節のどこを見たか」が変わる。お手本側の高さも同じ理由で、対応づいた点からでは
なくカーブの位置から決める（`ReferenceContour.centerLevel`）。下降声・上昇声は
カーブが声域を大きく縦断するので影響が大きく、実機で**同じ文を2回読んだだけで
同じ音節のお手本の高さが 0.99 と -0.36 に振れた**。

この修正で分離が大きく改善した。

| | つながりの誤差 |
|---|---|
| 正しい発話 | 0.001〜0.084（無声子音を90msまで入れて最大 0.246） |
| 声調の取り違え | 0.355〜1.645 |

**実際の声のばらつきと、取り違えの信号は重なっている**（合成音声での取り違えは
0.30〜0.95 に散る）。通す側に倒した結果、差の小さい対立は見逃す。

末尾の音節を別扱いにはしない。端だからと合格ラインを上乗せすると緩すぎになった
（中平声を下降声・高平声で発音しても通ってしまった）。

### 形が合っていても、それだけでは通さない

下降声・上昇声は動きそのものが情報なので形で判定するが、**形の一致だけで合格に
してはいけない**。上昇声を高平声で発音するとどちらも右上がりなので相関は 0.90 に
達するが、高さの関係は 1.17 も崩れている。形だけで見ていたとき、これが素通りした。

そこで形で通す場合にも、緩い高さの関門（`kContourLevelGate` = 0.5）を置く。
上の合格ラインより緩く、**明らかに崩れている場合だけを弾く**のが役目。

**関門は隣との段差ではなく、その音節自身の高さで見る。** 段差で見ると隣の誤りに
巻き添えになる。実機で、末尾の下降声が相関 0.99・高さのずれ 0.04 と完璧なのに、
隣が崩れているだけで落ちた。
絶対的な高さは本来は採点しないが（話者・場面で素直に動く）、関門としてなら使える。
実機の下降声・上昇声は正しく出せていれば 0.00〜0.31、取り違えは 0.71 以上に出る。

形の側の下限（`kShapeCorrelationThreshold`）は 0.4 と粗い。高さの関門と組みで
使うので、形だけで通ることはない。実機で相関 0.45・高さのずれ 0.00 という
「形はやや崩れているが高さは完璧」な発話が落ちたため下げた。声調の取り違えは
相関が 0.1 以下か負に出るので、この帯には入ってこない。

正しい発話は、無声子音・発話末の下がりを含む条件でも全音節が合格する。
声調の取り違えは16種のうち13種を弾く。通ってしまうのは次の3つ。

- **中平→低平**：5声調で最も差が小さい対立（0.355 対 正しい発話の上限 0.246）
- **末尾の 中平→低平**：文末はもともと下がる（final lowering）ので、低く言われても
  「下がりが少し深い」との区別がつかない（0.294）
- **下降→高平**：高平声は上がってから最後に落ちるので下降声と部分的に形が重なり、
  この文では高さの関係も 0.074 しか変わらない

**これ以上は締められない。** 正しい発話の値と取り違えの値が接する領域に入っており、
締めれば正しい発音を弾き、緩めれば誤りを見逃す。精度を上げるなら、話者ごとの
基準（同じ人の過去の録音）を積み上げる方向になる。

正しい発話に対して3倍前後の余裕を取る。実際の人の声は合成音声よりばらつくうえ、
判定が厳しすぎる発音練習は続かないので、迷ったら甘い側へ倒す。
ただし上限がある。緩めすぎると声調の取り違えが「合っている」に化け、
機能の中身が無くなる。

### 6. 抑揚なしの検出（monotone）

声調を付けず平坦に読み上げると、**中平声の音節だけが偶然一致して点数が半分近くまで伸びる**
（フェーズ0の合成音声で58点）。声調を教える機能としては甘すぎるので、別途旗を立てる。

この録音から声域を推定できず（広がりが `kMinRangeSemitone` 未満）蓄積プロファイルで
代替した場合、それが抑揚なしのシグナルになる。`PronunciationResult.isMonotone` が立つ。

UIでは点数の代わりに「抑揚が付いていません。声調を意識してもう一度」を出す。
点数より、次に何をすべきかが伝わる。

## 発音（子音・母音）の検査

声調とは別軸で「通じたか」を見る。声調が合っていても子音・母音を外していれば
語として通じないため、両方出さないと学習者は何を直せばよいか分からない。

端末の音声認識に例文を読ませ、認識結果に各語が順に現れるかを照合する
（`transcript_match.dart`）。**原価ゼロ・音声は端末外に出さない。**

### この検査の性質

音声認識は言語モデルで補正するため、多少外しても期待される語に「直して」認識する。
つまり**見逃す方向に甘い**。逆に認識できなければ「通じないレベルで外している」という
強い信号になる。したがって結果は「合っている／間違っている」ではなく
**「通じた／通じなかった」**として提示する。

1語聞き取れなかった時点で以降を全て missing に倒さないこと（照合カーソルを進めない）。
最初の1語を外しただけで文全体が真っ赤になり、どこが悪いか分からなくなる。

### マイクの一本化（重要）

録音プラグインと音声認識プラグインを並べると、**2つがマイクを奪い合って片方しか
動かない**。声調判定はPCMが必要、音声認識はプラットフォーム認識器がマイクを直接握る
ため、単純に足せない。

そのためマイクはネイティブ側の1箇所（`thai_memo/speech_capture` チャネル）だけが握り、
1本の音声をPCMと認識器の両方へ分岐させる。

- **iOS**: `AVAudioEngine` のタップを1つ張り、同じバッファを
  `SFSpeechAudioBufferRecognitionRequest` とPCMバッファへ渡す。
  `requiresOnDeviceRecognition` を必須とし、非対応端末では認識を諦める
- **Android**: PCM取得のみ（`transcriptAvailable = false`）。収録済み音声を
  `SpeechRecognizer` へ渡す `EXTRA_AUDIO_SOURCE` は API 33 以降でしか使えず、
  Android は未リリースのため実装していない

判定できないことと、判定して駄目だったことは UI でも分析でも必ず分ける
（`WordRecognition.unavailable` / `recognized_pct` を送らない）。

### 検証は実機でしかできない

**シミュレータでは発音チェックは必ず無効になる。** 端末内認識のアセットが無く、
`supportsOnDeviceRecognition` が false を返すため。マイク収録自体は Mac のマイクが
通るので、声調判定はシミュレータでも確認できる。

さらに**実機でも、その端末にタイ語の音声認識アセットが入っていなければ同じく無効**になる。
日本語話者の端末にタイ語ディクテーションが入っていることは稀なので、
**大半のユーザーで発音チェックが使えない可能性がある**。実機で最初に確認すべき点。

無効だった場合に「壊れているのか非対応なのか」を切り分けられるよう、ネイティブ側は
理由コードを返す（`recognitionStatus`）。**理由コードは画面にも出し、直せるものは
直し方まで案内する。** タイ語の音声入力を入れれば使えるようになる端末が大半なので、
「非対応です」で終わらせると直せる人まで諦める。

**設定アプリの該当画面へは飛ばせない。** `UIApplication.openSettingsURLString` は
自アプリの設定ページしか開けず、キーボード設定を直接開く `App-Prefs:` は非公開URLで
審査で弾かれる。案内は文言だけにする。

| 値 | 意味 |
|---|---|
| `ok` | 認識できた |
| `auth_denied` | 音声認識の許可が下りていない |
| `no_recognizer_for_locale` | th-TH の認識器が作れない |
| `recognizer_unavailable` | 認識器が一時的に使えない |
| `no_on_device_asset` | **端末内認識のアセットが無い**（シミュレータは必ずこれ） |
| `android_unsupported` | Android は未対応 |

### 自前ASRモデル（sherpa-onnx）を検討したが見送った

端末アセット依存を消すため、`sherpa_onnx` + `sherpa-onnx-zipformer-thai-2024-06-20`
（int8 約150MB）をアプリに載せる案を検証した。**採用しない。**

合成音声（macOS Thai TTS）で、正しい発話と「別の実在語に置き換えた発話」を作り、
誤りを検出できるかを測った結果:

| | 誤検出（正しい発話を通す） | 誤りの検出 |
|---|---|---|
| 素の認識精度 | 6/6 完全一致 | — |
| **分節音（子音・母音）** | 6/6 | **2/6** |
| 声調（参考） | 8/8 | 5/8 |

検出できたのは kh/k と母音の長短のみ。**ph/p・th/t・r/l・末子音 k/p はすべて見逃した**。
日本語話者が最も外しやすい対立ばかりで、しかもこれは合成音声での上限値。
150MB を投じて得られる感度ではない。

モデル自体の認識精度は高い（6/6 完全一致）。問題は精度ではなく、
**音声認識が言語モデルで期待される語へ補正してしまう**という原理的な性質にある。
同じ理由で他のASRに替えても大きくは変わらない。

検証スクリプトは `scratchpad/asr/eval.py`（再実行にはモデルの再取得が必要）。

### 分かったこと: SARA AM の表記ゆれ

検証中に照合側のバグを発見した。タイ文字の ำ は1文字（U+0E33）でも
2文字（U+0E4D U+0E32）でも書け、**Unicode の NFC では統一されない**。
認識器は分解形を返すことがあり、揃えないと ทำ・น้ำ・คำ・จำ のような頻出語が
すべて「認識されなかった」と誤判定される。`normalizeForMatch` で明示的に畳んでいる。

アセットが無い端末が多いようなら、端末外での認識（`requiresOnDeviceRecognition = false`）を
許すかの判断になる。**その場合は音声が端末外へ出るため、`NSMicrophoneUsageDescription` /
`NSSpeechRecognitionUsageDescription` の「端末の中だけで処理され、どこにも送信されません」
という記述を必ず書き換えること。**

### 表示

語ごとの帯は**1本**。声調と発音を合わせた総合判定を出す（`combinedWordVerdict`）。

当初は上段＝声調・下段＝発音の2本に分けたが、実機で見ると単に鬱陶しく、
どちらを見ればよいのか分からない。帯の役目は「この語を言い直す必要があるか」
だけを伝えることで、内訳は**語をタップしたときのカードで分ける**
（音節ごとの声調 ＋「発音：通じました／通じませんでした」の1行）。

合わせ方は次のとおり。

| 声調 | 通じた／未判定 | 通じなかった |
|---|---|---|
| ○ | ○ | × |
| 惜しい | 惜しい | × |
| × | × | × |
| 判定対象外 | 判定対象外 | × |

- **通じたことは加点にしない。** 音声認識は言語モデルで期待される語へ補正するため
  見逃す方向に甘く、通ったことは「正しい」の根拠にならない
- **通じなかった語は、声調が合っていても ×。** 帯が伝えるのは「この語を言い直す
  必要があるか」で、通じていない語は声調が合っていても言い直す必要がある。
  当初は一段だけ下げていた（○→惜しい）が、それでは発音の軸が単独では何も落とせず
  判定にほとんど効かなかった。認識が落ちる原因は発音以外（雑音・語彙）にもあるが、
  認識器はそもそも期待される語へ補正して返すので、それでも通らなかったことのほうが
  強い信号
- 発音を判定できない端末では帯が声調だけを表すので、凡例でその旨を出す
  （判定できないことと、判定して駄目だったことを混同させない）

### 総合点は声調と発音の半々

声調だけで点を出すと「全部通じていないのに高得点」になり、帯と点数が食い違う。

```
overallScore = toneScore × 0.5 + 通じた語の割合(0〜100) × 0.5
```

- 半々にするのは、どちらを外しても語として通じないから。優劣を付ける理由がない
  （`kToneScoreWeight` = 0.5）
- **判定していない端末では声調の点をそのまま返す。** 発音側を満点として足すと、
  対応していない端末のほうが点が出やすくなる
- 切り分け用に `toneScore` も結果に残し、ログに `tone=… -> overall=…` を出す

DB（`pronunciation_attempts.overall_score`）に入るのは総合点。声調のみだった
時期の値とは意味が変わる。

## 依存とパーミッション

現状、オーディオ録音の依存もマイク権限も**ゼロ**（`pubspec.yaml`・`Info.plist` とも該当なし）。

- `record` — マイク入力（PCMストリーム）
- `pitch_detector_dart` — YIN
- DTW・正規化・カーブ定数は自前実装
- iOS: `NSMicrophoneUsageDescription`（用途が明確なので審査リスクは低い）
- Android: `RECORD_AUDIO`

権限拒否時は練習セクションを非表示にし、設定への導線だけ出す。

## 課金

Premium限定とする（free は既存の「聞く」まで）。

**判定が完全にオンデバイスで完結するため原価はゼロ**。現在 Premium 165円/月の
LLM原価に上乗せがなく、利益率を下げずに訴求を1つ増やせる。

商用の発音評価API（Azure Speech / SpeechSuper / Speechace）も調査したが、
Azure は th-TH に対応する一方で**音節レベルのスコアと韻律評価が en-US 限定**であり、
「どの音節の声調を外したか」を返せない。声調評価を提供する商用APIは見当たらず、
自前実装が妥当という結論。子音・母音の正確さ（音素レベル）だけは Azure に
委ねるハイブリッドが将来の拡張として残る。

導入時は `paywallFeature*` のコピーを、抽象的な現行3項目から
発音練習を含む具体的なものへ差し替える。

## リスクと対策

| リスク | 対策 |
|---|---|
| 判定精度が低いと一発で信頼を失う | フェーズ0で実データを取り閾値を決めるまで本番に出さない。閾値は常に緩め側に倒す |
| YINのオクターブエラー | メディアンフィルタ必須。これが最も多い故障モード |
| 騒音環境での精度低下 | 信頼度が低いフレームが一定割合を超えたら採点せず「もう一度」を出す |
| お手本カーブ（理論値）とTTS音声のズレ | 許容する。お手本音声とカーブは別物という前提でUIを作る |
| 文が長いと全体やり直しになり挫折 | 語タップで部分リトライ（フェーズ2と共通の仕組み） |

## 実装順

1. **フェーズ0（完了）** — 判定ロジック（正規化・DTW・採点）を純粋な Dart 関数として実装。
   合成音声によるユニットテストで、声域差・話速差に影響されないこと、平坦3声調の
   取り違えを検出できることを確認済み
2. **フェーズ1（完了）** — `detail_screen` に練習セクションを追加。録音（`record`）、

3. **発音（通じたか）の検査（完了）** — 端末の音声認識との照合。iOSのみ
4. フェーズ2以降は別途

## 残っている調整

閾値 `kLevelErrorThreshold` / `kShapeErrorThreshold` は合成音声で妥当な緩めの値であり、
**実際の人の声では未検証**。実機で録音しながら詰める必要がある。

Android の発音検査は未実装（声調のみ）。入れる場合は API 33 以降で
`ParcelFileDescriptor` のパイプを `SpeechRecognizer` に渡す実装を足す。

音素レベルの本格的な評価が要るなら Azure Speech のハイブリッドが残っている
（th-TH の音素スコアが実際に返るかは要検証、約0.35円/回）。

GA4 のカスタムディメンション（`worst_tone` / `monotone` / `recognized_pct`）は未登録。
登録しないと `(not set)` になり遡及しないため、リリース前に登録すること。
