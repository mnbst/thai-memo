# 語彙スコア（estimated_vocab）算出ロジック

## 概要

`estimated_vocab` は「P(know) ≈ 0.5 となる freq_rank」として定義される語彙境界値。
単語の習熟確率 P が 0.5 を下回り始める rank = 「まだ覚えていない単語の入り口」を表す。

## 算出フロー

```
UVMドキュメント群（対象範囲のみ取得）
    ↓
回答済みの語だけで {rank: p} マップを構築
    ↓
AnsweredAvg(rank) を center ± 50 の範囲でスキャン（証拠の無い窓は飛ばす）
    ↓
AnsweredAvg < 閾値 となる最初の rank = estimated_vocab
（全て閾値超え → 証拠の上端 / 証拠なし → center のまま）
```

## 関数詳細

### `AnsweredAvg(wordsByRank, center, window=10)` — `internal/uvm/model.go`

rank `center` 周辺 ±10（21ランク）にある**回答済みの語だけ**の平均 P を返す。
未登録の rank は prior で埋めず、母数にも入れない。窓に 1 語も無ければ
`ok=false`（＝その rank については判定しない）。

以前は未登録 rank を `UnknownWordP = 0.4` で埋めていた。prior が閾値
`VocabCutoffP = 0.42` より下なので「証拠が無い＝境界の外」と読まれ、そこから

- 受験直後に測定値が `-VocabMaxDelta`/sync で削られる
- その対処として測定値以下だけ閾値を下げる分岐（`VocabCutoffPTested = 0.30`）
- 削られないよう `knownMaxRank`（P>0.5 の最大 rank）を `max()` で床に張る
- その床が一方向のラチェットになり、**1 問の正解が境界を恒久的に押し上げる**

という連鎖が出ていた。最後のものが実機での暴走（例文生成の確認クイズを回すだけで
`estimated_vocab` が伸び続ける）の直接の原因。prior 埋めをやめて 3 つとも廃止した。

### `EstimateVocab(entries, center)` — `internal/uvm/model.go`

語彙境界 rank を推定する。**語彙テストの受験有無で分岐しない。**
テストは `estimated_vocab` の初期値を書くだけで、以後は受験者も未受験者も
この 1 本を通る。`vocab_test_vocab` は測定の記録として残すだけ。

#### ステップ

1. `entries` のうち `Answered` の語だけから `{rank: p}` マップを構築
2. **center 決定**: 引数が 0 の場合は P加重平均 rank を使用
   ```
   center = Σ(p × rank) / Σp
   ```
3. **スキャン**: `center - 50` ～ `center + 50` を順に走査
   - 証拠の無い窓（`AnsweredAvg` が `ok=false`）は飛ばす
   - `AnsweredAvg(r) < VocabCutoffP (0.42)` となった最初の `r` を返す
4. **全ての窓が閾値を超えた場合**: 境界は証拠の上端より上なので、証拠のあった
   最も高い rank を返して上へ進ませる（`maxAnsweredRank`）
5. **証拠が 1 つも無い場合**: `center` をそのまま返す（＝動かさない）

呼び出し側（`SyncEstimatedVocab`）が差分を `±VocabMaxDelta` に丸めるので、
5 は「今の値を保持する」を意味する。空を 0 と読むと、受験直後やクイズを受けない
期間に値が削られていく。

#### 上端は窓の中心ではなく証拠の rank（`maxAnsweredRank`）

4 の「証拠の上端」に走査のループ変数 `r`（＝`AnsweredAvg` に渡した**窓の中心**）を
入れてはいけない。窓は `r ± answeredWindow(10)` と対称なので、証拠が rank 247 に
1 語あるだけで中心 237〜257 の 21 窓が点灯する。最後に点灯するのは中心が証拠より
10 上の窓なので、`top` に `r` を入れると返り値が **証拠 + 10** を指す。

`SyncEstimatedVocab` は例文生成（`generate_thai_sentence.go`）と毎日配信
（`deliver_daily_sentence.go`）でも走るため、クイズを 1 問も受けなくても 1 日十数回
sync が回る。その結果、語彙測定 250（証拠は測定前のクイズ由来で rank 247 付近）の
ユーザーが `VocabMaxDelta = 3` ずつ登って **257 で止まる**。247 と 257 の間は
未観測であって「知っている」ではないので、これは測定値・実力の両方からの
系統的な上振れ（最大 `answeredWindow` ぶん）だった。

`maxAnsweredRank(wordsByRank, r, answeredWindow)` で窓に入っている回答済み語の
最大 rank を取り、その最大値を `top` にする。上の例は 247 に収束する。

なお `VocabMaxDelta` は速度だけで到達点は変えない（clamp を外すと 1 回の sync で
250 → 257 に飛ぶだけ）。clamp は対称なので片道のラチェットでもない。

#### 閾値を割った窓は上限としてだけ使う

閾値を割った側（`return r`）も、窓の中心をそのまま返してはいけない。窓が対称な
以上、証拠に最初に触れる窓の中心は必ず「証拠の rank − `answeredWindow`」であり、
`KeyWordBand` の下端が境界そのものである以上、回答済み語は常に境界より上にある。
つまりこの `r` は**構造的に現在値より上を指す**。

    現在値 100 / 回答済みは rank130 の 1 語だけ
      r=120 の窓 (110-130) が証拠に触れる → avg=0.077 < 0.42 → return 120

rank130 を**間違えた**という証拠しか無いのに、境界が 100 → 120 へ登る。これが
「まとめクイズを 1 問も受けずに語彙スコアが上がる」の正体だった。

閾値割れは「その辺りは知らない」＝境界の**上限**の情報でしかないので、上昇には
使わない。

    return max(min(r, max(center, top)), 0)

`top` は閾値を超えた窓に入っていた回答済み語の最大 rank（＝実際に正解が積まれた
証拠）。正解の証拠が無ければ現在値より上へは動かず、下げるときはそのまま効く。

| 証拠（center=100） | 修正前 raw | 修正後 raw |
|---|---|---|
| rank130 を確認クイズで正解（P=0.149） | 120 | 100 |
| rank130 を誤答（P=0.077） | 120 | 100 |
| rank105 を誤答 | 95 | 95 |
| rank130 に正解の証拠（P=0.58） | 130 | 130 |

（`model_golden_test.go: TestScanBoundaryUnknownEvidenceDoesNotRaise`）

### 回答した語だけが境界を動かす（`RankedP.Answered`）

平均に入れるのは**クイズか語彙テストで回答した語だけ**。例文に出ただけ・
key_word として登録されただけの語（`NewWordP = 0.1`）は母数に入れない。

`NewWordP` は選定機構のための登録値であって「知らない」という証拠ではない。
そのまま平均に入れると、**key_word に選ばれること自体が境界を押し下げる**。
受験直後の 2〜4 週目に estimated_vocab が沈んでから戻る動きになっていた
（`sim_dip_test.go` / `sim_matrix_test.go`、1日5生成5クイズ・90日）。

| 真値 | クイズ | 修正前 測定→d30→d90 | 修正後 測定→d30→d90 |
|-----|-------|-------------------|-------------------|
| 700 | 5問/日 | 695 → 671 → 757 | 695 → 702 → 784 |
| 700 | 0問/日 | 695 → 637 → 647 | 695 → 696 → 696 |
| 350 | 5問/日 | 352 → 347 → 448 | 352 → 359 → 447 |
| 350 | 0問/日 | 352 → 312 → 332 | 352 → 354 → 354 |

修正後は沈まない。クイズを受けなければ測定値のまま動かないのも正しい挙動で、
修正前は例文を生成するだけで測定値から 40 下がっていた。

判定は `quiz_attempts > 0 || last_result != nil`。露出で作る doc は
`last_result = nil` / `quiz_attempts = 0`、クイズはどちらかを必ず書く
（`exposure.go` / `store.go`）。
語彙テストが書くのは「既存の語を間違えた」ときだけ（次節）。

### 語彙テストは既知語を作らない（`TestSeedP`）

語彙テストが UVM に書くのは**「既に登録されている語を間違えた」ときの P 半減だけ**。
正解は書かない（未登録語の誤答も書かない）。測定値は `estimated_vocab` に直接
入るので、正解を既知語として置き直す必要がない。

2026-09-04 までは測定した境界より下の正解に `TestKnownP`(0.8) を置いていた。廃止した理由:

- **再受験が巻き戻る。** 測定値を下げても前回の 0.8 は境界の上に残る。
  前回の 0.8 が窓の平均を押し上げ、以後の sync が `VocabMaxDelta` ずつ
  前回の測定値まで登り直す。
  1回目300 → 2回目100 で、約60回の sync（クイズ・例文生成・毎日配信で1日約10回、
  およそ6日）で 289 まで戻っていた
- **精度が上がらない。** 本番の帯（`KeyWordBand`）で30日回すと、置いても置かなくても
  d30 の差は数語。真値350 だけは置かないほうが真値に近い（440 → 399）。
  0.8 は上振れを固定していただけだった

副作用として、出題した語が `key_word` 候補（「未登録 or P=0」）に戻る。4択で当てた語を
学習に回すのは望ましい方向で、16語なので選定への影響もない。

種付けをやめたことで、受験直後の走査窓は空になる。`EstimateVocab` は
**証拠が 1 つも無ければ `center` をそのまま返す**（＝動かさない）。空を「語彙 0」と
読むと受験翌日の最初の数回の sync が `VocabMaxDelta` ずつ削り、その日のクイズの
上げ幅と相殺していた（真値350 で d1 が測定値から動かない）。空は「証拠が無い」で
あって「語彙 0」ではない。

### 受験者と未受験者で挙動を分けない

2026-09-04 まで、受験者だけに次の 2 つの特別扱いがあった。

- `VocabCutoffPTested = 0.30` — 測定値以下の rank だけ閾値を下げ、証拠の無い
  区間で測定値が削られないよう保護する
- `bandLow = max(estimated_vocab, vocab_test_vocab)` — key_word 帯の下端に
  測定値を使う

どちらも「prior(0.4) < 閾値(0.42) なので、証拠が無いだけで境界の外と読まれる」への
対症療法だった。同じ非対称が `knownMaxRank` の床も要求し、その床がラチェットに
なって暴走を生んでいた（`AnsweredAvg` の節）。

平均を回答済みの語だけで取るようにして、3 つとも廃止した。**語彙テストは
`estimated_vocab` の初期値を書くだけ**で、以後の推定も key_word 選定も受験者・
未受験者で同じ経路を通る。`vocab_test_vocab` は測定の記録として残すだけ。

`sim_matrix_test.go`（20試行平均・1日5生成5クイズ・90日）:

| 真値 | 受験+クイズ d90 | 未受験+クイズ d90 | 受験+クイズ無し d90 |
|-----|---------------|-----------------|-------------------|
| 150 | 240 | 235 | 110（測定値のまま） |
| 350 | 441 | 434 | 302 |
| 700 | 779 | 774 | 645 |

受験と未受験がほぼ同じ値へ収束し、クイズを受けなければ測定値を保つ。

**未解決:** どちらの経路も真値を上抜けする（真値150 で 240、真値350 で 441）。
これは境界推定ではなく α の大きさが原因で、rank>300 では 1 問正解で新規語の P が
0.1 → 0.550 と一撃で 0.5 を越える（`RankScaleFloorRank`）。

### 露出は回答済みの語の P を動かさない（`RegisterExposure`）

例文に出た語は `AlphaExposure=0.10` で P が微増し、`ExposureCap = UnknownWordP = 0.4`
で頭打ちになる。この底上げを当てるのは**未回答の語だけ**。

回答済みの語に当てていた頃は次の2つが出ていた。

- **確認クイズだけで境界が上がる。** `key_word` は自分が読んだ例文の語なので必ず
  露出済み。露出で 0.4 まで運ばれた語は、確認クイズ（`quiz_type="learning"`、
  `LearningCorrectMultiplier=0.1`）の正解 1 回で 0.428 となり
  `VocabCutoffP=0.42` を越える。上限が閾値の 0.02 下でしかないので、
  ×0.1 の減衰が意味を持たなかった
- **誤答の証拠が消える。** 不正解で 0.079 まで落ちた語も、例文に出続けるだけで
  0.4 に戻る。「知らないと分かった語」が境界を押し下げなくなる

### 等倍で採点されたクイズだけが境界を動かす（`graded`）

境界推定（`SyncEstimatedVocab`）の母数に入るのは、**α を減衰させずに採点された
回答**を 1 回でも持つ語だけ。判定は `IsGradedResult(quizType, result)` で

    quiz_type != "learning" && hint_level == 0 && !sentence_reviewed

のときだけ `uvm/{word}.graded = true` を立てる（`store.go`）。露出で作る doc は
`graded=false`（`exposure.go`）。一度立った `graded` は下ろさない。

減衰つきの回答が作る P は閾値に構造的に届かない。確認クイズの正解は α×0.1
（`LearningCorrectMultiplier`）で新規語なら P=0.145、ヒント有りは ×0.5/×0.25、
例文レビュー由来も ×0.1。`VocabCutoffP=0.42` を越えられないのに母数には入るので、
**未登録 rank の prior(0.4) より低い実測値**として窓の平均を押し下げ、走査が手前で
止まる。例文を生成するたびに境界が数ランク落ちていたのはこれ。

`dropsim_test.go`（1日5生成5確認クイズ＋まとめクイズ5問・90日＝生成450回・20試行平均）:

| 設定 | 真値150 d90 / 低下回数 | 真値350 | 真値700 |
|---|---|---|---|
| 実装前（全部を母数に） | 266 / 5回 | 447 / 5回 | 784 / 13回 |
| 実装前 + 前方を狭める(8) | 275 / 13回 | 434 / 10回 | 774 / 27回 |
| 実装前 + 前方を狭める(3) | 187 / 57回 | 402 / 51回 | 760 / 52回 |
| 実装前 + 前方を広げる(40) | 480 / 0回 | 578 / 0回 | 816 / 3回 |
| 実装後（等倍のみ） | 268 / 1回 | 445 / 1回 | 782 / 3回 |

`ScanBand` の前方幅では直らない。狭めると低 P の語が境界の判定窓（±10）の中へ
落ちるので低下が 2〜10 倍に増え、広げると低下は消えるが境界の上が prior のまま
走査が伸び続けて真値150 が 480 まで暴走する。母数の側を絞るのが正しい。

到達点は変わらない（266→268 / 447→445 / 784→782）。まとめクイズを放置したときに
測定値・現在値からまったく動かなくなるのが差分。

**移行:** `graded` を持たない既存 doc は母数に**入れる**（`boolField(..., true)`）。
デプロイの瞬間に母数が急減して estimated_vocab が動くのを避ける。新しく作られる
doc は必ずフィールドを持つので、下げ圧の原因になる語から順に外れていく。

### 測定値を下回らせない（`SyncEstimatedVocab`）

`estimated_vocab` は `vocab_test_vocab` を下限にする。未受験者は 0 なので無効。

前節の下降が受験者の目に見える形（測定100が数日で91まで落ちる）で出ていたことへの
歯止め。測定値は `ScoreBias` のぶん平均で真値より低く出る（真値150→測定122、
真値700→測定677）ので、下限に使っても上振れは固定しない。再受験すれば
`vocab_test_vocab` ごと下がる。

これは下限であって推定の分岐ではない。`EstimateVocab` も `KeyWordBand` も
測定値を見ない、という原則は変えていない。

### 測定値の上振れ補正（`ScoreBias`）

`ScoreVocab` は落ちた段を「推測補正した正答率 × 帯幅」で内挿するが、これは知識が
帯の中で一様に分布する前提。実際は帯の上へ行くほど落ちるので、推定は P=0.5 の
交点より上を指す。測定値から一律 `ScoreBias = 50` を引いて補正する。

| 真値 | 補正なし | 補正 25 | 補正 50 |
|-----|--------|--------|--------|
| 20 | +35 | +10 | −3 |
| 80 | +20 | −5 | −26 |
| 150 | +20 | −6 | −30 |
| 350 | +32 | +7 | −18 |
| 700 | +36 | +11 | −15 |

25 では中央帯（80〜700）が 5〜10 上振れて残る。上振れた出発点はそのまま
key_word 帯の下端（`KeyWordBand`）を押し上げ、クイズを受けない限り戻らない。下振れはクイズの正答で埋まるので、50 を採る。

（`sim_vocabtest_test.go` の測定精度表 / `sim_score_test.go`）

内挿の係数を縮める案も測ったが、真値20 付近は `max(vocab, passedHigh)` の床が
効いていて改善しない（内挿×0.4 でも +21）。段の構成にも内挿式にも触らない
一律減が一番素直に効く。

補正は `ScoreVocab` の中でかける。`estimated_vocab` が出発点であり、そのまま
`KeyWordBand` の下端になるので、上振れ込みの値を渡すと上振れた帯から始まる。

なおこの上振れ幅は `sim_vocabtest_test.go` の `pKnow`（scale=60 のロジスティック）を
真の知識曲線と仮定した数字。実際の学習者の曲線がこれより急なら補正は過剰になる。

### 出発点は語彙テストだけが決める（申告レベルは使わない）

`estimated_vocab` は 0 から始まり 1 回の sync で `VocabMaxDelta = 3` しか動かない。
既に数百語を知っている人が実力帯へ届くまでに数百セッション掛かるので、出発点を
一度だけ直接書く経路が要る。それが**語彙テスト**（`functions/go/vocabtest.go`）で、
`estimated_vocab` / `vocab_test_vocab` に測定値をそのまま入れる。

刻みを迂回する唯一の経路なので、受験は**週 1 回**（`vocabTestInterval`）に絞る。
数えるのは開始時刻（`vocab_test_window_at`）。締めた回が無い間だけ、同じ期間の
中で `vocabTestStartsPerWindow = 3` 回までやり直せる（通信断・誤タップからの
復帰用）。`resetLearningData` はこの 2 つを消さない（消せるとリセットで抜けられる）。

ヒアリングの `level` 回答（自己申告）はここに**一切入れない**。以前は
`vocab_floor` として下限に当てていたが、次の 2 つがあった。

- 申告の着地はクライアントからの書き込みで、`InterviewReporter` は失敗時に
  次回起動へ持ち越す。語彙テストより後に着地すると `vocab_floor_applied` との
  差分が「申告が変わった」と読まれ、測定値を申告値へ引き戻していた
- ランキングの上位帯（600）を、申告を選ぶだけで取れた

いまの `level` は分析用（`users/{uid}.interview`）にだけ残している。語彙テストの
開始段にも使わない（全員 1 段目から測る。申告で下の段を飛ばすと、その帯を
暗黙に通過扱いにするぶんスコアが上振れる）。

未受験のユーザーは 0 から `±VocabMaxDelta` で進む。実力との乖離が長く残るので
（真値 700 でも 30 日後に 160 程度: `sim_vocabtest_test.go` の「テスト無し」行）、
学習画面の `VocabTestReminderBanner` で受験へ誘導する。

`estimated_vocab` はクライアント書き込み禁止（firestore.rules）。
`leaderboard/{uid}` に複製される公開値なので、書けると順位を自己申告できてしまう。
旧 `vocab_floor` / `vocab_floor_applied` はサーバーが読まなくなった
（`resetLearningData` が既存 doc から削除する）。

なお語彙ランキングは**同じ帯（`vocabBands`）の中だけ**で順位を出す。

### `sync_estimated_vocab(db, uid, freq_rank)` — `uvm.py:116`

Firestoreの `users/{uid}.estimated_vocab` を効率的に更新する。

- 全UVMドキュメントを取得せず、`current_estimate ± 50` の範囲の単語のみ取得
- `estimate_vocab()` で再計算後、`merge=True` で書き込み

#### 呼び出しタイミング

| イベント | 呼び出し元 |
|---------|-----------|
| 例文生成後（exposure更新後） | `sentence_handlers.py` |
| クイズ結果更新後 | `uvm.py:batch_update_uvm()` |

## 定数

| 定数 | 値 | 用途 |
|------|----|------|
| `UnknownWordP` | 0.4 | `ExposureCap` の基準値（推定の prior としては使わない） |
| `VocabCutoffP` | 0.42 | スキャンを打ち切る平均 P の閾値 |
| `NewWordP` | 0.1 | UVM新規登録時の初期 P |

`TestKnownP`(0.8) は 2026-09-04 に廃止した（「語彙テストは既知語を作らない」を参照）。
`VocabCutoffPTested`(0.30) と `knownMaxRank` の床は 2026-09-04 に廃止した
（「受験者と未受験者で挙動を分けない」を参照）。

## 例

```
estimated_vocab = 600 のユーザーが rank=580〜620 の単語を習得した場合:
  → moving_avg がその帯域で 0.5 を超える
  → スキャンが rank=620 付近まで進んで初めて < 0.5
  → estimated_vocab ≈ 620 に更新
```
